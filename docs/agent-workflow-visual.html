ClaimLens 기획 및 AI Agent Workflow 정리

특허 초록 검색을 넘어 청구항 기반 기술 검토로 가는 Agent

ClaimLens는 제품 또는 기술 설명을 입력받아 관련 특허를 찾고, 독립항을 구성요소로 분해한 뒤 제품 기능과 행 단위로 비교해 claim chart와 기술 검토 초안을 만드는 프로젝트다. 핵심은 법률 판단이 아니라 근거가 남는 기술적 유사성 검토다.

Local DB First KIPRIS는 원천 데이터 공급원, 분석은 로컬 데이터 기반으로 수행
Claim Chart First 최종 리포트보다 청구항 구성요소별 비교표를 먼저 생성
Supervisor Agent 전문 Agent의 결과를 평가하고 재실행, 보강, 중단을 결정

프로젝트를 한 문장으로 설명하면

제품 기능과 특허 청구항을 직접 비교하기 어렵다는 문제를, 검색-상세조회-청구항분해-기능매칭-검증-보고서 생성의 구조화된 AI Agent workflow로 해결하는 포트폴리오 프로젝트다.

가장 좋은 발전 방향: V1 → V2 → V3

V1

Structured Workflow

Analyzer -> Search -> Parser -> Matcher -> Validator -> Report

  • 현재 설계의 기반
  • 구현과 테스트가 쉬움
  • 다만 면접에서는 LangGraph 파이프라인처럼 보일 수 있음
V2

Supervisor Multi-Agent

Supervisor -> Specialist Agents

  • Search, Claim, Parsing, Matching, Validation, Report 역할 분리
  • Supervisor가 결과 품질을 보고 다음 Agent를 선택
  • 포트폴리오 표현이 Multi-Agent Patent Analysis System으로 강해짐
V3

Reflection Loop

Validate -> Reflect -> Re-plan -> Retry

  • 근거 부족, 파싱 실패, 후보 부족을 스스로 감지
  • Supervisor가 Search/Parsing/Matching Agent를 재실행
  • 재계획, 자기검증, 실패 복구가 들어가 Agentic AI 느낌이 강해짐

보강된 기획: Supervisor + Specialist Agents

Supervisor Agent

전체 분석 상태를 관리하는 조정자

Supervisor Agent는 직접 모든 분석을 수행하지 않는다. 대신 제품 설명의 충분성, 검색 결과 수, 청구항 확보 여부, 파싱 신뢰도, 매칭 근거, 보고서의 법률 표현 위험을 확인하고 어떤 Specialist Agent를 다시 실행할지 결정한다. 이 구조가 ClaimLens를 단순 파이프라인이 아니라 상태 기반 멀티에이전트 시스템으로 만든다.

Search Agent

특허 후보 탐색

검색어 생성, 로컬 DB 검색, 벡터 검색, KIPRIS 보강 필요 여부를 담당한다.

Claim Agent

청구항 확보/선별

상세조회 결과에서 청구항을 추출하고 삭제항 제외, 독립항 판별을 수행한다.

Parsing Agent

구성요소 분해

독립항을 비교 가능한 claim element로 나누고 파싱 신뢰도를 반환한다.

Matching Agent

제품 기능 매칭

제품 기능과 청구항 구성요소를 행 단위로 비교하고 evidence를 붙인다.

Validation Agent

근거 검증/리포트 제한

근거 없는 matched를 차단하고 법률 침해 단정 표현을 제거한다.

검색 결과 부족

candidate_count < threshold이면 Supervisor가 Search Agent에 검색어 재작성 또는 KIPRIS 보강을 지시한다.

파싱 신뢰도 낮음

parser_confidence < threshold이면 Parsing Agent를 한 번 재실행하고, 실패 시 uncertain으로 유지한다.

매칭 근거 부족

evidence_missing이면 Matching Agent를 재실행하거나 Validation Agent가 matched를 uncertain으로 낮춘다.

Reflection Loop 예시

Validation

근거 부족 감지

matched 결과에 제품 기능 근거가 없거나 claim element와 연결이 약함.

Supervisor

재계획

현재 후보만으로는 비교가 약하다고 판단하고 Search Agent 재실행 결정.

Search

검색 보강

검색어를 넓히거나 KIPRIS live enrichment로 추가 후보를 확보.

Matching

재비교

새 후보 또는 보강된 청구항으로 제품 기능 매칭을 다시 수행.

Decision

통과/다운그레이드

근거가 충분하면 유지하고, 여전히 약하면 uncertain으로 낮춤.

전체 데이터 흐름

1. Input

제품/기술 설명

사용자가 제품 기능, 서비스 구조, 기술 설명을 입력한다.

2. Search

로컬 후보 검색

저장된 초록, 메타데이터, 청구항 임베딩으로 후보 특허를 찾는다.

3. Enrich

KIPRIS 보강

청구항이 없거나 후보가 부족할 때만 KIPRIS 상세조회를 호출한다.

4. Compare

청구항 비교

독립항을 구성요소로 나누고 제품 기능과 행 단위로 비교한다.

5. Report

검토 초안

claim chart를 기반으로 기술적 위험과 불확실성을 요약한다.

KIPRIS 호출 정책

  • getAdvancedSearch: 키워드 검색으로 후보와 출원번호 확보
  • getBibliographyDetailInfoSearch: 출원번호 기반 상세조회로 청구항 확보
  • 10건 검색 시 최악의 경우 검색 1회 + 상세 10회로 11회 호출 가능
  • 월 1,000회 제한 때문에 매 분석마다 live fetch하면 안 됨
  • 한 번 가져온 특허와 청구항은 DB에 저장하고 재사용해야 함

DB에 축적해야 하는 이유

  • 외부 API 응답 속도와 장애에 분석 품질이 흔들리지 않게 함
  • 청구항 원문, 정규화 결과, 독립항 여부를 반복 활용할 수 있음
  • 분석 결과를 재현하고 면접에서 시스템 설계를 설명하기 쉬움
  • API quota를 검색/보강 단계에만 사용해 비용과 제한을 관리함
  • seed dataset 50-100건을 만들면 데모 안정성이 크게 올라감

Agent Workflow

Agent 입력 담당 책임 출력 Supervisor 판단 기준
Supervisor Agent 제품/기술 설명 전체 상태 관리, 다음 Agent 선택, 재시도/중단/fallback 결정 agent_state, decisions, retry_count 입력이 모호하면 추가 입력 요청, 충분하면 Search Agent 실행
Search Agent 검색어, 제품 기능 로컬 DB 키워드 검색과 벡터 검색으로 후보 특허 탐색 patent_candidates 후보 수가 부족하면 검색어 재작성 또는 KIPRIS live enrichment
Claim Agent 후보 특허 로컬 청구항 조회, 누락 시 KIPRIS 상세조회로 보강 claims, fetch_status 청구항이 없으면 후보 제외 또는 claim_unavailable로 표시
Parsing Agent 청구항 원문 삭제항 제외, 독립항 판별, 구성요소 분해 claim_elements 신뢰도가 낮으면 한 번 재시도, 실패하면 full claim을 uncertain element로 보존
Matching Agent 제품 기능, 구성요소 구성요소별 제품 기능 매칭과 근거 생성 claim_chart_rows matched, partial은 evidence가 있어야 유지
Validation Agent claim chart 근거 없는 matched 결과 차단, 형식 검증 validated_rows 근거가 약하면 Matching Agent 재실행 또는 uncertain으로 downgrade
Report Agent 검증된 claim chart 기술 검토 초안과 불확실성 요약 final_report Validation Agent가 법률 단정 표현을 검사하고 필요 시 재작성

AI Agent의 자율성은 무엇인가

자율적으로 하는 것

Supervisor가 Agent별 결과를 보고 Search, Claim, Parsing, Matching, Report Agent 중 어느 역할을 다시 실행할지 결정한다.

자율적으로 하면 안 되는 것

침해 여부를 단정하거나, 근거 없는 매칭을 만들거나, KIPRIS를 무제한 호출하거나, 청구항 없이 claim chart를 생성하지 않는다.

멀티에이전트 의미

각 Agent는 검색, 청구항, 파싱, 매칭, 검증처럼 책임이 분리되어 있고 Supervisor가 상태와 품질 기준으로 조정한다.

SSE로 보여줄 것

어떤 Agent가 실행됐는지, Supervisor가 왜 재실행을 결정했는지, fallback reason과 claim chart row를 실시간으로 보여준다.

초록의 역할

  • 관련 특허 후보 검색
  • 기술 분야 파악
  • 검색 랭킹 보조
  • 분석 대상 선별

청구항의 역할

  • 권리 범위의 핵심 텍스트
  • 독립항 중심 비교
  • 구성요소별 claim chart 생성
  • 제품 기능과 직접 매칭

검증의 역할

  • 근거 없는 matched 차단
  • 삭제 청구항 제외
  • claimCount와 실제 item 수 차이 처리
  • 법률 판단 표현 제거

면접에서 알아야 하는 설명 포인트

질문 짧은 답변
왜 초록만 쓰지 않나요? 초록은 후보 검색에는 좋지만 권리 범위 비교에는 부족합니다. claim chart는 청구항, 특히 독립항이 필요합니다.
KIPRIS를 왜 매번 호출하지 않나요? 월 호출 제한과 응답 안정성 때문에 KIPRIS는 원천 데이터 수집/보강에 쓰고, 분석은 local DB를 우선합니다.
이게 그냥 RAG와 다른 점은? 검색 결과를 바로 요약하지 않고 청구항 분해, 제품 기능 매칭, 검증된 claim chart를 거쳐 보고서를 만듭니다.
Agent가 자율적이라는 뜻은? Supervisor Agent가 Search, Claim, Parsing, Matching, Validation Agent의 결과를 보고 재실행, 보강, 중단을 결정한다는 뜻입니다.
왜 멀티에이전트 구조가 맞나요? 특허 분석은 검색, 청구항 확보, 독립항 파싱, 제품 기능 매칭, 근거 검증의 책임이 명확히 나뉘기 때문에 역할 분리가 자연스럽습니다.
환각은 어떻게 줄이나요? 최종 답변을 바로 만들지 않고 claim chart row마다 근거를 요구하며, 근거 없는 결과는 uncertain으로 낮춥니다.

구현 우선순위

Step 1

KIPRIS Collector

검색과 상세조회 응답을 normalize하고 patents, claims에 저장한다.

Step 2

Seed Dataset

RAG, 문서검색, OCR, AI 검색 도메인의 50-100건을 수집한다.

Step 3

Claim Parser

삭제항 제외, 독립항 판별, 구성요소 분해를 안정화한다.

Step 4

LangGraph

검색, 보강, 파싱, 매칭, 검증, 보고서 노드를 연결한다.

Step 5

SSE UI

Agent timeline, tool call, claim chart row를 실시간 표시한다.
