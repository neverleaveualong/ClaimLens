ClaimLens Database Schema

왜 이 스키마로 나누는가

ClaimLens의 DB는 KIPRIS 원본을 그대로 저장하는 영역과, AI Agent가 분석을 위해 만든 가공 데이터, 그리고 사용자가 실행한 분석 결과를 분리한다. 핵심은 원본 보존, 분석 재사용, 결과 추적이다.

1. KIPRIS 원본 저장

특허 기본정보와 청구항 원문을 보존한다. KIPRIS 응답과 가장 가깝다.

patents claims

2. AI 분석용 가공

청구항을 구성요소로 쪼개 Agent가 비교할 수 있는 단위로 만든다.

claim_elements

3. 사용자 분석 결과

사용자 입력과 claim chart 결과를 저장해 재현 가능하게 만든다.

analysis_runs claim_charts

관계로 보면 이렇게 된다

patents 1 : N claims
claims 1 : N claim_elements
analysis_runs 1 : N claim_charts
claim_charts N : 1 claim_elements

1대1 매핑인가?

claims까지는 거의 1대1

KIPRIS의 claimInfo 하나가 claims row 하나가 된다. 삭제 청구항도 row로 저장하되 분석에서는 제외한다.

claim_elements는 1대N

청구항 하나를 여러 구성요소로 쪼갠 결과다. KIPRIS 원본에는 없는 ClaimLens 가공 데이터다.

claim_charts는 분석 실행마다 생성

같은 청구항이어도 사용자 제품 설명이 다르면 매칭 결과가 달라지므로 analysis_run별로 저장한다.

실제 데이터가 흘러가는 예시

KIPRIS 응답

claimInfo.claim = "1. 문서가 저장되는 데이터베이스; 사용자가 질의어를..."

claims 저장

raw_text 보존, normalized_text 정리, is_independent=true 저장

claim_elements 생성

데이터베이스, 입력수단, 키워드 추출수단, 가중치부여수단 등으로 분해

claim_charts 생성

사용자 제품 기능과 각 구성요소를 matched, partial, not_found, uncertain으로 비교
